System One vs LLM:
Jev는 무엇을 받고 무엇을 돌려주는가

코드를 한 줄도 쓰지 않고, Jev 호출 한 건의 요청과 응답을 해부한다. 이 한 장이 앞으로 모든 설계 레슨의 좌표계다.

미션 연결

Jev를 하네스 안에 설계해 넣으려면 먼저 "무엇이 들어가고 무엇이 나오는가"를 정확히 알아야 한다. 질문 설계(레슨 2~3), 임계값(레슨 4), 아키텍처(레슨 5)는 모두 오늘 배우는 요청/응답 모양 위에 얹힌다.

오늘의 한 가지 승리

레슨을 마치면 Jev 요청/응답 JSON을 보고 각 필드가 무엇인지 말할 수 있고, LLM 호출과 무엇이 다른지 세 가지로 설명할 수 있다.

1. 두 가지 계약

LLM은 사람이 읽을 텍스트를 만들도록 설계됐다. 그런데 우리는 자주 LLM에게 "판정"을 시키고, 그 텍스트를 다시 파싱해서 코드가 쓸 수 있는 값으로 되돌린다. TypeSafe는 이것을 불일치(mismatch)라고 부른다: 텍스트 생성기를 억지로 구조화된 결정기로 쓰고 있다는 것이다.1

1 공식 Introduction 페이지의 첫 단락. docs.typesafe.ai/introduction (이 환경에서는 GitHub 미러로 읽을 수 있다.)

Jev는 다른 계약을 제안한다. state(판단 재료)와 타입이 정해진 질문들을 보내면, 타입이 정해진 답과 확률이 돌아온다. 텍스트 생성도, 파싱도 없다.2 TypeSafe는 이런 모델 클래스를 System One Model이라 부르고, Jev가 그 첫 모델이다.

2 "No text generation, no parsing. You get typed values and probability distributions that your code can branch on, sort by, and route with." — Introduction.

LLM 텍스트 계약

  • 입력: 프롬프트(텍스트)
  • 출력: 텍스트(토큰을 순서대로 생성)
  • 코드가 쓰려면 파싱·검증 필요
  • 답과 함께 설명·근거를 써 줄 수 있음
  • 답 공간이 열려 있음(무엇이든 쓸 수 있음)

System One · Jev 결정 계약

  • 입력: state + 타입 질문(Choice/Score/Noul)
  • 출력: 타입 값 + 확률 분포 + confidence
  • 코드가 바로 분기·정렬·라우팅에 사용
  • 답장·코드·근거 설명을 만들지 않음3
  • 답 공간은 내가 질문에서 미리 정의
3 "System One models do not write replies, produce code, or generate explanations of their reasoning. You define the possible answers through primitives." — System One 개념 페이지.

이름은 카너먼의 Thinking, Fast and Slow에서 왔다. System 1은 빠르고 직관적인 판단, System 2는 느리고 신중한 추론. Jev는 "지식 있는 사람이 맥락만 주면 몇 초 안에 내릴 수 있는 직감 판정"을 겨냥한다.4 확장 추론이 필요한 질문은 Jev 것이 아니다. 쪼개서 여러 개의 직감 판정으로 바꾸거나, LLM에게 넘긴다.

4 "Think of each question as a gut-check determination: the kind of judgment a highly knowledgeable person could make in a few seconds given the right context." — Introduction, "Atomic questions, composed in code".
내 코드state를 조립하고 질문을 정의
→
Jev모든 질문을 병렬·독립으로 판정
→
내 코드답·확률·confidence로 분기, 합산, 라우팅

제어 흐름은 항상 코드가 소유한다. Jev는 흐름 속의 "판정 한 칸"을 맡는다. 이 그림은 레슨 5(하네스 안의 4가지 위치)에서 다시 확장한다.

2. 세 가지 프리미티브

Jev에 던질 수 있는 질문은 딱 세 종류다. TypeSafe는 이를 소프트웨어 프리미티브에 빗대어 AI 프리미티브라 부른다.5

5 표의 예시 문구와 예시 출력은 System One 개념 페이지의 것을 그대로 옮겼다. "These are illustrative configurations and values."
프리미티브질문의 형태답 공간(예)반환 필드
Choice"이 티켓은 어느 팀이 맡아야 하나?"billing / technical / accountchoice, probabilities, confidence
Score"이 고객은 얼마나 화가 났나?"0 침착 · 1 불만 · 2 매우 화남score, legend, probabilities, confidence
Noul"이 메시지는 환불을 요청하는가?"참 / 거짓noul (0~1)

세 종류를 한 번의 호출에 섞어 보낼 수 있고, 모든 질문은 같은 state에 대해 병렬로, 서로 격리되어 평가된다. 질문을 더해도 응답 시간은 거의 늘지 않고, 한 질문의 답이 다른 질문을 오염시키지 않는다.6 이것이 다음 레슨들에서 "쪼개서 여러 개 묻기"가 공짜에 가까운 이유다.

6 "Every question is evaluated in parallel and in isolation against the same state in one go. Adding questions barely changes the response time. … adding more questions does not create context-rot." — Introduction.

3. 요청 한 건 해부

공식 Quick start의 예제를 그대로 가져왔다.7 고객 지원 메시지 하나를 state로 넣고 세 가지 질문을 동시에 던진다. 필드마다 색을 달았다: 파랑은 키, 주황은 내가 쓰는 문자열, 회색 기울임은 주석이다.

7 docs.typesafe.ai/introduction/quickstart, "Request body" / "Response body". 엔드포인트는 POST https://api.typesafe.ai/v1/systemone.
{
  "state": "Hi, I've been trying to connect my Stripe account for 3 days
            and it keeps failing. I'm losing sales. Please help ASAP.",
            ← 판단 재료. 문자열·JSON 객체·텍스트 배열 가능. 텍스트만.
  "model": "jev-latest",       ← 어느 모델이 처리할지. SDK 기본값도 이것.
  "questions": {
    "department": {                ← 질문 ID. 내가 붙이는 이름, 모델에는 전달되지 않음.
      "type": "choice",
      "instructions": "Which team should handle this",   ← 질문 본문
      "criteria": {                    ← 답 공간: 옵션 이름 → 설명
        "billing":   "Payment or subscription issues",
        "technical": "Bugs or integration problems",
        "sales":     "Pricing or account questions"
      }
    },
    "frustration": {
      "type": "score",
      "instructions": "How frustrated the customer appears",
      "criteria": [                    ← 답 공간: 낮음→높음 순서 배열 (레벨 0,1,2)
        "Calm, just stating facts",
        "Frustrated but civil",
        "Very angry, strong language"
      ]
    },
    "is_urgent": {
      "type": "noul",
      "instructions": "The message conveys urgency or time-sensitivity"
    }                                  ← Noul은 criteria가 선택 사항. 명제 하나면 충분.
  }
}

세 가지를 눈에 새기자. 첫째, 답 공간은 내가 쓴다. criteria에 없는 값은 절대 돌아오지 않는다. 둘째, 질문 ID는 모델이 보지 못한다. 그래서 instructions에 완전한 질문을 써야 한다.8 셋째, state 하나에 질문 세 개. 호출은 한 번이다.

8 이 규칙은 Primitives 페이지에 있다. department라는 ID를 보고 모델이 "부서를 묻는구나"라고 추론하지 않는다.

4. 응답 한 건 해부

{
  "model": "jev-latest",
  "answers": {
    "department": {
      "type": "choice",
      "choice": "billing",               ← 가장 확률 높은 옵션
      "probabilities": {                ← 전 옵션의 확률. 합은 1.
        "billing": 0.84, "technical": 0.159, "sales": 0.001
      },
      "confidence": 0.596             ← 분포가 얼마나 몰려 있는가. "맞을 확률"이 아님!
    },
    "frustration": {
      "type": "score",
      "score": 1.035,                   ← 레벨 사이 값 가능(확률 가중 평균)
      "legend": { "0": "Calm…", "1": "Frustrated but civil", "2": "Very angry…" },
      "confidence": 0.842
    },
    "is_urgent": {
      "type": "noul",
      "noul": 0.999                     ← 명제가 참일 확률. confidence 필드 없음.
    }
  },
  "usage": { "input_tokens": 312, "output_tokens": 48 }
}

여기서 가장 자주 오해되는 것이 confidence다. confidence는 "이 답이 맞을 확률"이 아니다. 확률 분포의 형태(얼마나 한 옵션에 몰려 있는가)에서 계산한 통계다.9 위 예에서 billing이 0.84인데 confidence는 0.596이다. 0.84라는 큰 확률이 있어도 나머지 0.16이 technical에 꽤 몰려 있으니, 분포는 "완전히 확신"과는 거리가 있다는 뜻이다. Noul은 이미 확률 하나가 답이므로 confidence가 따로 없다.

9 Confidence 페이지. 리서치 노트 research/jev-use-cases.md 3.1절에 요약. confidence로 "언제 행동하고 언제 사람에게 넘길지"를 정하는 방법은 레슨 4에서 다룬다.

그리고 캘리브레이션은 집합의 성질이다. 잘 캘리브레이션된 모델이 0.8을 매긴 사건들은 전체적으로 약 80% 일어난다. 하지만 개별 0.8 하나가 맞다는 보장은 아니다.10 이 문장을 정확히 말할 수 있으면, "Jev는 환각이 없다"는 마케팅 문구도 정확히 번역할 수 있다: 스키마 밖 값은 안 나오지만, 스키마 안에서 틀린 옵션을 고를 수는 있다.

10 "Calibration is measured across groups of predictions; it does not guarantee that an individual answer is correct." — System One 개념 페이지. 학습법 RLCD(Reinforcement Learning for Calibrated Decisions)는 AI primer에 있고, 레슨 6에서 다룬다.

5. 연습

즉시 피드백이 나온다. 위로 스크롤하지 말고 기억으로 답해 보자. 틀려도 좋다. 틀린 것이 더 오래 남는다.

고객 이메일을 받아 세 줄 요약문을 만들어야 한다. 누구의 일인가?

  • Jev — 문서 판정은 System One의 영역이다
  • LLM — 열린 텍스트 생성은 LLM의 영역이다
  • 둘 다 가능 — 질문 설계만 잘 하면 된다

지원 티켓을 billing / technical / sales 세 큐 중 하나로 보내야 한다. 누구의 일인가?

  • Jev — 닫힌 답 공간에서 고르는 직감 판정이다
  • LLM — 사람 말을 이해해야 하므로 LLM이다
  • 코드 — 키워드 매칭으로 충분히 처리된다

요청 JSON에서 모델이 보지 못하는 것은?

  • state 문자열 안의 고객 메시지 본문
  • criteria 안의 각 옵션에 대한 설명
  • questions 아래의 각 질문 ID 이름

응답에서 department의 choice는 billing(0.84)인데 confidence는 0.596이다. 이 0.596의 뜻은?

  • billing이 정답일 확률이 약 60%라는 뜻이다
  • 확률 분포가 한 옵션에 몰린 정도의 통계다
  • 모델이 state를 이해한 정도를 나타낸다

세 프리미티브 중 응답에 confidence 필드가 없는 것은?

  • Noul
  • Score
  • Choice

한 요청에 질문을 3개에서 10개로 늘리면?

  • 응답 시간이 대략 세 배 이상 길어진다
  • 앞 질문의 답이 뒤 질문의 문맥이 된다
  • 시간은 거의 같고 각 질문은 독립이다

"Jev는 캘리브레이션되어 있다"의 정확한 뜻은?

  • 0.8을 받은 답은 각각 80% 확률로 맞다
  • 0.8을 받은 사건 집합이 약 80% 일어난다
  • 스키마 안에서는 틀린 옵션을 고르지 않는다

6. 말로 설명해 보기

화면을 보지 말고 소리 내어 답해 보자. 이건 채점하지 않는다. 대신 답한 문장을 에이전트(나)에게 그대로 보내면 피드백을 주고, 잘 됐으면 학습 기록으로 남긴다.

  1. Jev 호출과 LLM 호출의 차이를 세 가지로 말해 보라. (힌트: 입력, 출력, 답 공간)
  2. "Jev는 환각이 없다"를 정확한 문장으로 다시 말해 보라.
  3. confidence 0.596을 팀 동료에게 한 문장으로 설명해 보라.
