jev-tech · 레슨 0002 · 약 30분

state 하나가 분류되는 흐름을
손으로 따라가기

지원 티켓 한 장이 들어와서 "billing 팀으로, 환불 요청 있음"이라는 결정이 나오기까지, 여섯 칸을 한 칸씩 밟는다. 어디까지가 코드 일이고 어디부터가 Jev 일인지 손가락으로 가리킬 수 있게 되는 것이 목표다.

왜 이 레슨인가

레슨 1 뒤에 "state가 주어지고 분류되는 흐름이 아직 잘 안 잡힌다"는 질문이 나왔다. 정확한 지적이다. 레슨 1은 요청·응답의 모양만 보여줬고, 그 사이에서 무슨 일이 일어나는지와 응답을 받은 코드가 무엇을 하는지는 비어 있었다. 오늘 그 빈칸을 채운다.

오늘의 한 가지 승리

티켓 세 종류를 시뮬레이터에 넣어 보고, 어느 티켓이 왜 사람 검토로 가는지 코드의 어느 줄에서 갈렸는지 짚어 말할 수 있다.

1. 먼저 그림 하나

TypeSafe가 권하는 아키텍처는 딱 한 문장이다: 평범한 소프트웨어 워크플로를 만들고, AI가 필요한 자리에만 System One을 끼워 넣는다.1 제어 흐름·결정적 규칙·부작용(이메일 발송, 환불 실행)은 전부 코드가 가진다. Jev는 "이 문장은 어느 팀 얘기인가" 같은 상식 판단 한 칸만 맡는다.

1 "Summary: build a normal software workflow and insert System One only where AI is needed." — How to build with TypeSafe. 이 레슨의 시나리오·질문·분기 코드는 모두 이 페이지의 triage_ticket.py 예제를 단순화한 것이다.
① 원본 데이터티켓, 고객, 정책… 앱이 가진 전부
→
② state 조립코드가 걸러내고 필요한 것만 이름 붙여 담음
→
③ 요청state 1개 + 질문 N개
→
④ Jev질문마다 옵션 위에 확률 배분, 병렬
→
⑤ 응답choice/score/noul + 확률 + confidence
→
⑥ 코드 분기임계값 비교, 가중 합산, 라우팅

여섯 칸 중 Jev가 하는 일은 ④ 하나다. ②와 ⑥이 설계의 대부분이고, 그것은 전부 코드(=내가 정하는 것)다. 이 비율을 몸에 새기는 것이 오늘의 절반이다.

2. ④에서 실제로 무슨 일이 일어나나

레슨 1에서 나온 질문을 여기서 정면으로 답한다. Jev는 트랜스포머 신경망이다. state와 질문 텍스트(instructions, criteria)를 함께 한 번 읽는다.2 LLM이라면 이 지점에서 첫 토큰을 뽑고, 그 토큰을 다시 입력에 붙여 두 번째 토큰을 뽑는 식으로 수십~수백 번 신경망을 돈다. Jev는 그렇게 하지 않는다. 내가 criteria에 적어 준 옵션들(billing / orders / account)이 곧 후보이고, 한 번의 계산으로 그 후보들 위에 확률을 나눠 준다. 옵션이 셋이면 숫자 셋, 질문이 다섯이면 그 다섯 묶음이 동시에 나온다.

2 구조 세부(병렬 샘플러, RLCD 학습)는 레슨 6에서. 지금 필요한 것은 "후보를 만들어내는 게 아니라 내가 준 후보에 점수를 매긴다"는 한 문장이다. 공식: "Because every output is constrained to the supplied options, the model returns a full probability distribution over those options rather than inventing a value outside the schema." — How to build.

그래서 출력 토큰이 거의 없고 값싸다. 응답 JSON은 모델이 "쓴" 것이 아니라, 그 확률표를 서버가 서식에 맞춰 적어 준 것이다. Thinking 단계도 없다. 판단이 여러 요인에 걸쳐 있으면 모델이 생각을 더 하는 게 아니라, 내가 질문을 여러 개로 쪼개서 ④에 병렬로 넣는다. 이것이 레슨 3의 주제다.

3. 시뮬레이터: 티켓 세 장, 여섯 칸

아래에서 티켓을 고르고 "다음"을 눌러 한 칸씩 이동해 보라. 셋 다 같은 질문 세 개를 받지만, ④의 확률 모양이 다르고, 그래서 ⑥에서 다른 곳으로 간다. 특히 티켓 C가 어디서 갈리는지 보라.3

3 ④의 막대 값은 학습용 추정치다. 실제 Jev를 호출한 결과가 아니다. 실제 값은 모델 버전과 질문 문구에 따라 달라지므로, 숫자가 아니라 분포의 모양이 분기를 어떻게 바꾸는지에 집중하라.

4. ⑥의 코드를 읽어 보기

시뮬레이터의 마지막 칸이 따라간 코드다. 공식 예제를 세 질문 버전으로 줄였다.4 코드를 쓰라는 것이 아니다. 어느 줄이 어떤 응답 필드를 읽는지만 따라가라.

4 원본 triage_ticket.py는 스팸 신호 Noul 세 개를 코드에서 0.45/0.30/0.25 가중 합산하는 부분도 있다. 그 "여러 답을 코드에서 합치기"는 레슨 3에서 다시 만난다.
# ② 코드: 결정적 규칙 먼저. 닫힌 티켓은 모델을 부르지도 않는다.
if ticket.status == "closed": return "no_action"

# ② 코드: 질문에 필요한 필드만 골라 state 조립
state = { "ticket": {...}, "customer": {...} }

# ③ 요청 → ④ Jev → ⑤ 응답
answers = client.system_one(state=state, questions=questions).answers

# ⑥ 코드: 먼저 "모르겠다" 신호를 잡는다
if answers["topic"].confidence < 0.75:          ← 분포가 퍼져 있으면 사람에게
    return route_to_human_review(ticket)

# ⑥ 코드: 답(choice)으로 분기. 미리 물어둔 답은 이 경로에서만 쓴다
if answers["topic"].choice == "billing":
    return route_to_billing(ticket,
        refund_requested = answers["refund_requested"].noul >= 0.7)

if answers["topic"].choice == "orders":
    return route_to_orders(ticket)

# ⑥ 코드: Score는 score와 confidence를 함께 본다
priority = "high" if (answers["frustration"].score >= 1.5
                      and answers["frustration"].confidence >= 0.7) else "normal"
return route_to_account_support(ticket, priority=priority)

세 가지를 보라. 첫째, 첫 번째 if는 답이 아니라 confidence를 본다. "무엇"보다 "행동해도 되는가"를 먼저 묻는다.5 둘째, 0.75, 0.7, 1.5는 전부 코드에 있다. Jev는 임계값을 모른다. 셋째, refund_requested는 세 티켓 모두에게 물었지만 billing 경로에서만 읽는다. 미리 물어두고 코드가 필요할 때만 쓰는 것을 공식 문서는 speculative fan-out이라 부른다.

5 "High confidence: act automatically. Medium: proceed with caution. Low: do not act. Where you draw those boundaries depends on the stakes." — Confidence. 임계값을 어떻게 정하는지는 레슨 4.

5. 연습

시뮬레이터를 다시 열지 말고 기억으로. 틀리면 해설을 읽고, 그 다음에 시뮬레이터로 확인하라.

고객 객체에는 주문 20건이 있는데 state에는 배송 중인 2건만 들어갔다. 이 걸러내기는 누가 했나?

  • Jev — 질문과 무관한 필드를 스스로 무시한다
  • API — 토큰 예산에 맞춰 자동으로 잘라 준다
  • 코드 — state 조립 단계에서 개발자가 골랐다

④에서 Jev가 topic 질문에 답할 때, 후보 billing / orders / account는 어디서 왔나?

  • 내가 요청의 criteria에 적어 보낸 것이다
  • Jev가 state를 읽고 스스로 후보를 만들었다
  • TypeSafe가 미리 정해 둔 표준 분류 체계다

티켓 C의 응답: topic.choice = "billing", topic.confidence = 0.31, refund_requested.noul = 0.62. 코드는 어디로 보내나?

  • route_to_billing — choice가 billing이므로
  • route_to_human_review — confidence가 0.75 미만
  • route_to_account_support — 기본 경로로 떨어진다

티켓 A에서 refund_requested.noul = 0.96이 "환불 요청 있음"으로 처리됐다. "있음"이라고 결정한 것은?

  • Jev — noul이 0.5를 넘으면 참으로 반환한다
  • API — 응답에 true/false 필드가 함께 온다
  • 코드 — noul >= 0.7 비교식이 결정했다

티켓 A는 billing으로 갔다. 그럼 frustration 질문의 답은?

  • 나왔지만 이 경로의 코드가 읽지 않았다
  • billing으로 갈 것을 알고 Jev가 건너뛰었다
  • 코드가 두 번째 요청으로 따로 물어야 한다

④에서 LLM과 Jev의 결정적 차이를 한 문장으로 고르면?

  • LLM은 영어만, Jev는 여러 언어를 함께 읽는다
  • LLM은 답을 토큰으로 만들고, Jev는 준 옵션에 확률을 매긴다
  • LLM은 한 질문씩, Jev는 여러 질문을 순서대로 처리한다

6. 말로 설명해 보기

다음 셋을 소리 내어 말한 뒤, 그 문장을 나에게 보내 달라. 잘 됐으면 첫 학습 기록으로 남긴다.

  1. 여섯 칸을 순서대로 말하고, 각 칸이 코드 일인지 Jev 일인지 붙여라.
  2. 티켓 C가 사람 검토로 간 이유를 응답 필드 이름을 써서 한 문장으로.
  3. "Jev가 왜 출력이 싼가"를 ④의 관점에서 두 문장으로.
