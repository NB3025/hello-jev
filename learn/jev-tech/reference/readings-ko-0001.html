1. Introduction

원문: docs.typesafe.ai/introduction · 미러: 001-introduction

Jev is TypeSafe's flagship model and the first System One model. Send state and typed questions; get structured answers your code can use directly.

Jev는 TypeSafe의 대표 모델이자 첫 System One 모델이다. state와 타입 질문을 보내면, 코드가 바로 쓸 수 있는 구조화된 답을 받는다.

대규모 언어 모델(LLM)은 사람이 읽을 텍스트를 만들도록 설계됐다. 코드가 소비할 판단(judgment)을 모델에게 시켜야 할 때, 여기서 불일치(mismatch)가 생긴다. 텍스트 생성 시스템을 억지로 구조화된 결정을 출력하게 만들고, 그 결과를 다시 파싱해서 코드가 의존할 수 있는 무언가로 되돌리는 셈이다.

Jev는 TypeSafe의 대표 모델이자 첫 System One 모델이다. System One 모델은 소프트웨어가 직접 쓸 수 있는 빠르고 구조화된 결정을 내리도록 만들어졌다. Jev는 타입이 정해진 질문들을 state에 대해 평가하고, 구조화된 결과를 바로 돌려준다. 텍스트 생성도 없고, 파싱도 없다. 코드가 분기하고(branch on), 정렬하고(sort by), 라우팅할 수 있는(route with) 타입 값과 확률 분포를 받는다.

TypeSafe 프리미티브

TypeSafe는 세 가지 AI 프리미티브를 제공한다. 소프트웨어 프리미티브와 비슷하게, AI 프리미티브는 모듈화되어 있고, 조합 가능하고, 구조화되어 있고, 신뢰할 수 있고, 빠르다. 각각 다른 종류의 질문을 던지고 다른 종류의 답을 돌려준다.

질문 유형목적반환
Choice목록에서 하나를 고른다choice, probabilities, confidence
Score루브릭 위에서 state에 점수를 매긴다score, probabilities, confidence
Noul이 진술은 참인가?noul (0~1)

세 질문 유형은 한 번의 API 호출에 섞어 쓸 수 있다. 모든 질문은 같은 state에 대해 한 번에, 병렬로, 서로 격리되어 평가된다. 질문을 더해도 응답 시간은 거의 변하지 않는다. 각 질문은 독립적으로 평가되므로, 질문을 더 넣어도 컨텍스트 부패(context-rot)가 생기지 않는다.

원자적 질문, 코드에서 조합

System One 모델은 각 질문이 하나의 구체적이고 범위가 잘 잡힌 것을 물을 때 가장 잘 작동한다. 각 질문을 직감 판정(gut-check determination)이라고 생각하라. 매우 지식이 많은 사람이 적절한 맥락만 주어지면 몇 초 안에 내릴 수 있는 종류의 판단이다.

묻고 싶은 질문이 확장된 추론을 요구하거나 여러 독립 요인을 저울질해야 한다면, 분해하라. 각 요인을 별도 질문으로 묻고, 결과를 코드의 로직으로 결합하라. 이렇게 하면 각 평가가 신뢰할 수 있게 유지되고, 차원별 가중치를 어떻게 줄지 완전히 통제할 수 있다.

예를 들어 "이 스타트업 피치를 평가하라" 대신, 시장 크기·기술적 실현 가능성·차별화를 따로 물어라. 점수는 자신의 공식으로 결합하라. 우선순위가 바뀌면 프롬프트를 다시 쓰는 대신 코드의 계수 하나를 바꾸면 된다.

2. System One

원문: docs.typesafe.ai/concepts/system-one · 미러: 003-system-one

System One models make fast, structured decisions for software. Jev is TypeSafe's flagship model and the first System One model.

System One 모델은 소프트웨어를 위한 빠르고 구조화된 결정을 내린다. Jev는 TypeSafe의 대표 모델이자 첫 System One 모델이다.

System One 모델은 소프트웨어가 직접 쓸 수 있는 빠르고 구조화된 결정을 내리도록 만들어진 AI 모델 클래스다. System One 모델은 state를 평가하고 타입 답과 확률을 돌려준다.

Jev는 TypeSafe의 대표 모델이자 첫 System One 모델이다.

LLM처럼 System One 모델도 자연어 입력을 이해한다. 다만 생성된 텍스트 대신 타입 결정과 확률을 돌려준다.

Jev는 현재 텍스트 입력만 받는다. 문자열, JSON 객체, 텍스트 배열을 평가한다. 이미지·오디오·비디오는 (아직) 지원하지 않는다.

LLM과 어떻게 다른가

System One 모델은 캘리브레이션된 결정을 위해 학습된다. 확률이 결과(outcome)에 맞춰 최적화되어 불확실성을 반영한다. 캘리브레이션은 예측들의 집합에 대해 측정된다. 개별 답이 옳다는 보장은 아니다.

System One 모델은 답장을 쓰지 않고, 코드를 만들지 않고, 자기 추론에 대한 설명을 생성하지 않는다. 가능한 답은 당신이 프리미티브로 정의한다.

프리미티브질문답 공간 예출력 예
Choice이 티켓은 어느 팀이 처리해야 하나?billing, technical, accountchoice: "billing"
Score이 고객은 얼마나 화가 났나?0 = 침착, 1 = 불만, 2 = 매우 화남score: 1.4
Noul이 메시지는 환불을 요청하는가?참 또는 거짓noul: 0.95

이것들은 예시 구성과 값이다. 각 프리미티브 페이지에 사용 가능한 설정 옵션과 전체 응답 필드가 있다.

System One 모델이 어떻게 작동하고 어떻게 학습되는지는 AI primer를 읽어라.

System One이라는 이름은 대니얼 카너먼이 Thinking, Fast and Slow에서 대중화한 개념에서 왔다. System 1 사고는 빠르고 직관적이다. System 2는 느리고 신중하다. 여기서 강조점은 빠르고 초점이 좁은 판단이다.

더 큰 워크플로 안의 빠른 판단

환불 요청을 예로 들면, 애플리케이션은 이렇게 할 수 있다.

  1. 고객 메시지, 관련 거래 내역, 환불 정책을 담은 state를 만든다.
  2. 독립적인 질문들을 함께 묻는다. 환불이 요청되었는가, 증거가 중복 결제를 가리키는가, 정책이 환불을 지지하는가.
  3. 답을 코드의 결정적(deterministic) 검사와 결합하고, 케이스를 처리 또는 검토로 라우팅한다.

프리미티브가 작동하는 것을 봤다면, 더 큰 시스템으로 조합할 수 있다. System One 모델은 자유 형식 텍스트가 아니라 타입이 있고 제약된 출력을 돌려주므로, 코드가 그 답을 검사하고 조합해 예측 가능한 워크플로를 만들 수 있다. 전체 워크플로는 How to build with TypeSafe를 보라.

System One 모델의 답에는 confidence도 포함되므로, 언제 행동하고 언제 사람이나 추론 모델로 에스컬레이션할지 결정할 수 있다.

System One 모델 호출하기

클라이언트 SDK 중 하나로, 또는 HTTP API의 POST /v1/systemone으로 System One 모델을 호출한다. model 필드가 어느 모델이 요청을 처리할지 고른다. 이 문서의 예제는 jev-latest를 쓰며, SDK 기본값도 같다. 사용 가능한 모델·가격·별칭은 Models를 보라.

입력 준비는 State에서, 던질 수 있는 질문 유형은 Primitives (Questions)에서 시작하라.

3. AI primer

원문: docs.typesafe.ai/introduction/machine-learning-primer · 미러: 010-ai-primer · 역주 레슨 6(원리)의 선행 자료. 지금은 훑어만 봐도 된다.

Why TypeSafe trains decision models with calibrated probabilities instead of optimizing for generated text.

TypeSafe가 생성 텍스트를 최적화하는 대신, 캘리브레이션된 확률을 가진 결정 모델을 학습시키는 이유.

대부분의 AI 제품은 모델과 사람 사이의 대화를 중심으로 만들어진다. TypeSafe는 다른 베팅에서 출발한다. 대규모 자동화는 AI-대-AI, AI-대-소프트웨어 상호작용이 지배할 것이므로, 채팅 인터페이스보다 기계 인터페이스가 더 중요하다는 것이다.

우리는 이것을 Machine Native Intelligence(기계 네이티브 지능)라 부른다.

구조, 신뢰성, 관측 가능성, 테스트 가능성, 속도, 일관성, 저비용처럼 소프트웨어 같은 속성을 가진 AI.

God이 아니라 prod를 만든다

TypeSafe는 모든 것을 하는 모델을 만들려는 것이 아니다. 코드가 검사하고 행동할 수 있는 좁은 결정이 필요한 프로덕션 시스템을 위해 설계됐다.

우리의 예상은 대규모 AI 자동화가 99% 기계-대-기계 상호작용, 1% 사람 상호작용에 가까울 것이라는 것이다. 이 예상은 설계 목표를 "읽기 좋은 응답"에서 "소프트웨어 안에서 예측 가능하게 행동하는 출력"으로 옮긴다.

TypeSafe 매니페스토를 읽어라.

세 가지 사후 학습(post-training) 접근

사전 학습된 언어 모델은 두 가지 주요 방식으로 조정되어 왔다. TypeSafe가 세 번째를 더한다. RLHF와 RLVR은 맥락을 위해 보여주는 것이고, TypeSafe의 학습 경로는 RLCD다.

방법풀어 쓰면무엇을 만들었나
RLHFReinforcement learning from human feedback (사람 피드백 기반 강화학습)사전 학습 모델을 챗봇으로 바꿨다. 사람이 선호하는 응답을 내도록 학습시킨다.
RLVRReinforcement learning with verifiable rewards (검증 가능한 보상 기반 강화학습)수학 같은 과제에 강한 추론 모델을 만들었다. 다만 더 느리고 비싸다.
RLCDReinforcement learning for calibrated decisions (캘리브레이션된 결정을 위한 강화학습)TypeSafe가 생성 텍스트 대신 결정과 캘리브레이션된 확률을 돌려주도록 학습시킨다.

RLHF는 InstructGPT와 ChatGPT 학습에 쓰였고, TypeSafe 공동창업자 Diogo Almeida가 공동 발명했다.

(원문 그림: 사전 학습 언어 모델에서 흐릿한 RLHF·RLVR 경로와 강조된 RLCD 결정 모델 경로가 갈라진다.)

RLCD와 캘리브레이션된 결정

RLCD는 다른 출력 계약을 최적화한다.

  • 모델은 텍스트를 생성하지 않는다.
  • 결정과 확률을 돌려준다.
  • 확률이 높을수록 답이 옳을 가능성이 커야 한다.

캘리브레이션은 불확실성을 소프트웨어가 쓸 수 있게 만든다. 잘 캘리브레이션된 모델의 많은 예측에 걸쳐:

  • 확률 0.2를 받은 결과는 약 20% 일어나야 한다.
  • 확률 0.8을 받은 결과는 약 80% 일어나야 한다.
  • 확률 1.0을 받은 결과는 100% 일어나야 한다.

이 비율은 예측들의 집합을 설명하는 것이며, 어느 한 답에 대한 보장은 아니다. 소프트웨어가 언제 행동하고 언제 에스컬레이션해야 하는지에 대한 안내는 Confidence를 보라.

RLHF의 문제

RLHF는 모델에게 사람이 선호하는 말을 하도록 가르친다. 그 목표는 챗봇에 잘 맞지만, 아첨(sycophancy)과 자신감 있게 들리는 환각에도 보상을 줄 수 있다.

선호 최적화는 mode dropping(모드 탈락)도 일으킨다. 모델이 지시 따르기 같은 특정 스타일을 선호하도록 학습하면서, 다른 가능한 출력의 확률을 줄인다.

(원문 그림: 기반 모델의 확률 분포와, RLHF 뒤에 좁아지고 모드가 탈락한 분포의 비교.)

출력이 사람에게 설득력 있어도, 무인 자동화에 충분히 신뢰할 만하지는 않을 수 있다. 사람의 선호와 기계의 신뢰 가능성은 서로 다른 최적화 목표다.

Mode dropping은 mode collapse(모드 붕괴)의 온건한 버전이다. 고전적인 생성적 적대 신경망(GAN)의 실패 모드에서, 생성기는 판별기를 계속 속이는 한 종류의 출력을 반복해서 만들도록 학습한다.

(원문 그림: 반복되는 캐릭터들로 모드 붕괴를 겪는 GAN을 묘사.)

RLHF는 대화형 모델에 여전히 잘 맞는다. TypeSafe의 입장은, 프로덕션 자동화에는 다른 학습 목표가 필요하다는 것이다. 제약된 결정과 캘리브레이션된 불확실성을 중심에 둔 목표다.

역주 · 이 페이지가 말하지 않는 것

RLCD의 보상 함수, 학습 데이터, 재현 가능한 평가는 공개되지 않았다(Turing Post, systemonemodels.org). 이 페이지는 "왜"를 설명하지만 "어떻게"는 설명하지 않는다. 레슨 6에서 공개된 범위와 그렇지 않은 범위를 구분해 다룬다.
